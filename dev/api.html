Declaring targets ​

Targets.target Function
julia
target(name, f; deps = nothing, format = :jld2, pattern = nothing, cue = :thorough,
       seed = :auto, slots = 1, deployment = :spawn)

Declare a target. Unless deps is given, dependencies are the argument names of f, which must therefore have exactly one method with positional arguments.

format is how the value is stored: :jld2 (the default), :jls (Serialization: fast, but tied to the Julia version), another format name made available by a package extension, a StorageFormat value carrying options, :file for a target that returns paths of files it reads or writes, or :url for one that returns URLs whose changes (by HTTP HEAD) should rebuild its consumers.

seed controls the random number generator f runs with: :auto seeds it from the pipeline seed and the target's name (see tar_seed), an integer pins the seed, and nothing leaves the session's generator alone.

slots and deployment matter for concurrent builds (tar_make(; jobs)). slots is how many of the jobs the target occupies while it runs (an integer, or :all to run with nothing else alongside); it controls what is started next to the target, not how many threads the target itself uses (see tar_slots). deployment = :main runs the target in the task that called tar_make, never at the same time as another :main target, for code that is not safe to run concurrently.

error says what a failure of this target does: :stop (the default) stops the build unless tar_make(; keep_going = true); :continue never stops it, but blocks the target's descendants; :null gives consumers nothing so they still run; :trim (branching targets) leaves failed branches out of the target's value. In every mode the failed target is retried on the next build.

retries reruns a failing target up to that many more times within one build, waiting retry_delay seconds between attempts, for flaky I/O. Every attempt uses the same seed, so retrying a deterministic failure is pointless.

julia
tar_pipeline(targets...; track = [], seed = 0)

Build a Pipeline. Arguments may be targets, @targets fragments or (nested) collections of them, so comprehensions and tar_map results can be passed directly. seed is the pipeline seed: changing it rebuilds every target with seed = :auto.

Targets.Pipeline Type
julia
Pipeline

A validated, immutable collection of targets with its dependency graph. graph has an edge dep => dependent; order is a deterministic build order. track lists extra modules or directories whose code counts as user code. groups maps each tar_map template name to its generated targets. seed is the pipeline seed that per-target seeds are derived from.

Targets.@pipeline Macro
julia
@pipeline [track = [...]] [seed = ...] begin
    @target name = expression [format = ...] [pattern = ...] [cue = ...] [seed = ...]
    @quarto name = "report.qmd" [options...]
    ...
end

tar_pipeline of the @targets fragment the block declares, with the given options.

When tar_make and the other functions load a pipeline script, a @pipeline or @targets block written at its top level runs one line at a time, which is much faster for large blocks and declares the same targets with the same hashes.

source
Targets.@targets Macro
julia
@targets begin
    @target name = expression [options...]
    @quarto name = "report.qmd" [options...]
    variable = value
    other_fragment
    ...
end

A Fragment of targets, to pass to tar_pipeline (or to splice into another block). Each @target's dependencies are the targets its expression refers to: names its expression binds itself (comprehension variables, lambda arguments, let bindings, ...) and variables of the block are not targets. A name that is neither a target nor defined where the block is written is an error when the pipeline is assembled, so fragments in different files can refer to each other's targets.

Besides @target and @quarto lines, a block may assign variables that its targets share (directory = "output"), and contain expressions whose value is a fragment, a target or a collection of them, such as a fragment returned by a function. Each @target's expression is what gets hashed, so reformatting never rebuilds; the values it captures from the block (and any local variables of an enclosing function) are hashed too.

A target's own name in its expression is never a dependency (@target summary = summary(fit) calls the function summary). Calling a function that has the same name as a target is an error, since the name means the target.

Targets.tar_quarto Function
julia
tar_quarto([name,] path; deps = [], extra_files = [], output = nothing,
           params = (;), quarto_args = [], quarto = "quarto", restart = true,
           quiet = true, kwargs...)

A target that renders the Quarto document path (a .qmd file) with the quarto CLI. name defaults to the file's stem (reports/summary.qmd is :summary). Relative paths are relative to the directory of the pipeline script (_targets.jl).

Its dependencies are the targets the document's executable Julia cells (and inline Julia code, the documents it includes with Quarto's include shortcode, and the Julia files its code loads with include("file.jl"), includet or include(joinpath(@__DIR__, ...)), recursively) read with tar_read(:name) or @tar_load name, found without running anything, plus deps. Cells marked #| eval: false are skipped. Reads whose name, and includes whose path, is not a literal give a warning: list those in deps and extra_files. The values are not passed in: the document reads them from the store, which is the one tar_make is building (see tar_read).

It is a file target whose files are the outputs followed by the document, the files it includes (documents and Julia files) and extra_files (e.g. a bibliography). So it is rebuilt when any of them changes in content (not when the files are only touched), when an output is deleted, or when a target it reads changes. Code the document loads from packages (using MyAnalysis) is not tracked; code in the Julia files it includes is, by their text.

The outputs are output when given, else the document's stem with the extension of each format in its front matter (or chosen with --to in quarto_args), html by default, plus the <stem>_files directory if Quarto writes one. params (a NamedTuple or Dict of numbers, booleans, strings and symbols) sets the document's parameters (quarto render -P key:value), which it declares with defaults under params: in its front matter; changing one rebuilds the report. Each render restarts Quarto's Julia worker for the document, so edited code is never stale (restart = false keeps it, which is faster), and refreshes Quarto's cache. quiet = false prints Quarto's output in the REPL while it renders, but only when the build runs one job at a time (jobs = 1, the default): with more jobs the output of concurrent renders would interleave, so it stays quiet without editing the pipeline. By default the output is shown only if the render fails. Neither changes when the report rebuilds. quarto is the Quarto executable. Other keyword arguments go to target (cue, error, retries, ...).

source
Targets.@quarto Macro
julia
@quarto name = "path.qmd" [option = value ...]

Declare a tar_quarto report inside @targets or @pipeline; the second form names it after the file (reports/summary.qmd is summary). Options are the keyword arguments of tar_quarto. Elsewhere, call tar_quarto.

Static branching and replication ​

Targets.tar_map Function
julia
tar_map(template, values; names = nothing)

Static branching: call template(value) for each element of values and give every target it returns a suffix, so :fit becomes :fit_ols. A dependency (or pattern) naming another target from the same template call is renamed with the same suffix; any other dependency is left alone. template returns a target or a collection of targets.

Returns a NamedTuple mapping each template name to its generated targets (m.fit == [fit_ols, fit_lasso]); pass it to tar_pipeline and combine a group with tar_combine.

Suffixes come from names when given: a collection with one suffix per element, or a function of the element. Otherwise, for each element:

  • the key, when values is a NamedTuple or AbstractDict;

  • the element itself, when it is a Symbol, string or integer, or a tuple of those (joined with _, for crossings from Iterators.product);

  • its position (1, 2, ...) otherwise.

julia
m = tar_map((ols = OLS(), lasso = Lasso(0.1))) do model
    (
        target(:fit, raw -> fit(model, raw)),          # fit_ols, fit_lasso
        target(:summary, fit -> summarize(fit)),       # depends on fit_ols / fit_lasso
    )
end
tar_pipeline(target(:raw, load), m, tar_combine(:all, (xs...) -> reduce(vcat, xs), m.summary))
source
Targets.@map Macro
julia
@map(values; names = nothing, prefix = false) do value
    @target ...
    ...
end

Inside @targets or @pipeline, declare the block's targets once for each element of values, as tar_map does: each name gets the element's suffix (fit_ols), or, with prefix = true, starts with it (ols_fit). names chooses the suffixes, as in tar_map. The block may use value, assign variables and splice in fragments, like any @targets block, and @maps nest.

Within a branch, a name refers to that branch's target. Outside the @map, a template's name refers to all of its targets: its value is a NamedTuple keyed by suffix (nested for nested @maps), so collect(chain) gives the values in order.

Targets.tar_rep Function
julia
tar_rep(name, f; batches, reps, deps = nothing, kwargs...)

Run f batches * reps times, as batches branches of reps replications each, for simulations with many cheap repetitions. f takes the values of its dependencies (by argument name, or deps) and each replication runs with its own seed, derived from the branch seed and its index, so results do not depend on how the work is batched across runs. Returns three targets: name_batch (the batch numbers), name_batches (one branch per batch) and name, the vector of all replications in order, which is what consumers should use. Other keyword arguments go to the batch target (see target).

source

julia
tar_map_rep(name, f, values; batches, reps, names = nothing, kwargs...)

tar_rep for each element of values, as with tar_map: f receives the element first, then its dependencies. Returns the tar_map groups, so m.name lists each element's vector of replications.

source
Targets.@rep Macro
julia

Inside @targets or @pipeline, tar_rep of expression: it is evaluated batches * reps times, as batches branches of reps replications, each with its own seed. Declares name_batch, name_batches and name, the vector of all replications, as tar_rep does; the other options are target's, for the branching target.

julia
StorageFormat

Supertype of storage formats. A format F defines

  • Targets.format_name(::F)::Symbol, the name recorded in metadata,

  • Targets.extension(::F)::String, the object file extension (without the dot),

Building ​

Targets.tar_make Function
julia
tar_make(p::Pipeline; names = nothing, force = false, store = default_store_path(),
         root = nothing, keep_going = nothing, track_manifest = false,
         check_stale = true, jobs = nothing, executor = nothing,
         check_mutation = false,
         io = stdout, progress = :auto)

Build the targets of p that are outdated, in dependency order, and return a BuildSummary. With names, only those targets and everything they depend on are considered. With force = true, all of those are rebuilt whatever their status. An error stops the run and is rethrown, unless keep_going is set, in which case independent targets are still built, the failed targets' descendants are blocked, and every failure is returned in the summary: its errors maps each failed target or branch to its message, and the log ends with the same list. Without keep_going, it is the on_error preference of Targets: "stop" (the default) or "continue" (keep going). Set it for a project in LocalPreferences.toml:

toml
[Targets]
on_error = "continue"

Targets that need no build never wait for a job: every target that is up to date is reported before the first job starts, and a target whose upstream was rebuilt to the same value is settled as soon as that upstream finishes. To see what a build would do without building, call tar_outdated with the same names.

root is the project directory whose code counts as user code (default: the active project); p.track adds more. When the Manifest changes, a warning names the packages that moved, or with track_manifest = true everything is rebuilt. With check_stale, the run errors if a tracked source file changed on disk after this session loaded it (unless Revise is loaded), since the hashes would then describe code the session is not running.

Values are kept in memory only while a target in this run still needs them, so memory use follows the width of the pipeline, not its length.

With jobs = n, up to n independent targets and branches run at once, each as a Julia task; targets on the longest remaining path (by their last build times) start first. jobs = :auto is one job per thread of the default threadpool (Threads.nthreads(:default), so 1 when Julia runs on one thread). jobs counts tasks, not threads: more jobs than threads still overlap targets that wait on I/O (downloads, files, external commands), but CPU-bound targets only take turns, so start Julia with threads (e.g. julia -t 8) to run them in parallel. Without jobs (or executor), it is the jobs preference of Targets, else 1; only then is the preference read. Set it for a project in LocalPreferences.toml:

toml
[Targets]
jobs = "auto"   # or a number such as 4

A target occupies its slots of the n while it runs, and deployment = :main targets run in the calling task. Concurrent targets share the process: they must not cd, change ENV or mutate their arguments (consumers of one upstream share its value), and BLAS-heavy targets may want BLAS.set_num_threads(1). After a failure, running jobs are finished and committed before the error is rethrown; on interrupt, running jobs are waited for (interrupt again to abandon them).

check_mutation = true hashes every argument before and after each call and errors, naming the target and argument, if a target modified its input. It is costly, so it is off by default; turn it on in tests and CI.

Progress is logged to io and to _targets/log/progress.log, one line per finished target or branch: ✔ name 1.2s (reason) in green, ✖ name: error in red. With progress = :live (the default :auto picks it when io is a terminal), the jobs still running stay in a footer below the log, each with a spinner and its time so far, above a count of the targets done, running and queued; console log messages from targets are printed above the footer, but what targets print straight to stdout can disturb it until the next redraw. With progress = :lines, a ▶ name (reason) line also marks each start.

Targets.BuildSummary Type
julia
BuildSummary

Names of targets that were built, found up to date (skipped), failed (errored) or not attempted because an upstream target failed (blocked), each in build order. branches maps each branching target to the ids of the branches that were (re)built in this run, and trimmed each error = :trim target to the ids of the failed branches left out of its value. errors maps the key of every target ("name") and branch ("name/id") that failed in this run to its error message.

Targets.tar_outdated Function
julia
tar_outdated(p::Pipeline; names = nothing, store = default_store_path(), root = nothing)

Targets that a build would have to rebuild, with the reason for each, as a vector of (; name, reason) in build order. Conservative: without building, it cannot know whether a rebuilt upstream will produce the same value, so every descendant of an outdated target is reported as :upstream_outdated (a real build may still skip some of them through early cutoff). tar_outdated() with no argument loads _targets.jl.

Executor

Where jobs run. An executor has a capacity (slots), submit!(exec, job, slots) starts a job, and take_result!(exec) waits for the next JobResult. start! and stop! bracket a build. See TaskExecutor.

source

source
Targets.DistributedExecutor Type
julia
DistributedExecutor(pids; script = joinpath(project_root(), "_targets.jl"),
                    slots_per_worker = 1)

Run jobs on Distributed worker processes (for example from addprocs, ClusterManagers.jl or SlurmClusterManager.jl), each with slots_per_worker slots. Needs using Distributed. Functions are never sent between processes: each worker loads script itself and looks targets up by name, and the build aborts if a worker's code hashes differ from the main process's. Workers write objects to the store, which must be on a filesystem they share with the main process (checked at start-up); only hashes and record fields come back, and the main process alone writes metadata. Arguments are sent to the worker with the job. deployment = :main targets still run in the main process.

Reading and managing the store ​

Targets.tar_read Function
julia
tar_read(name; store = default_store_path(), script = nothing,
         on_outdated = default_on_outdated())

The stored value of target name. For a file target this is its path (or vector of paths), relative to the project root; for a branching target it is the vector of its branch values in pattern order.

The value is the last one stored, even if the target is no longer up to date. on_outdated says what happens then: :warn (the default), :error, or :ignore (which also skips the check). Set the default for a project with the on_outdated preference, e.g. in LocalPreferences.toml:

toml
[Targets]
on_outdated = "error"

When reading the project's own store, the check is tar_outdated on the project's _targets.jl (or on script), so code edits count. Otherwise, and for targets no longer in the pipeline, only an invalidated target (one with no build record) counts as outdated.

Without store, the store is _targets in the project root, or the path in the store preference of Targets (relative to the project root). In a Quarto notebook (the julia engine) rendered by tar_quarto during tar_make, it is the store that build uses, and the check is skipped since the build has just updated what the document reads. A notebook rendered by hand can name its store in its front matter, relative to the document:

yaml
targets-store: ../_targets

Viewing the pipeline ​

Targets.tar_list Function
julia
tar_list(p::Pipeline; names = nothing, descendants = false)

List the pipeline's targets without their dependencies, as a TargetList. Targets are grouped into constants, input files, computations and output files (file and URL targets count as files), and the list is split by the connected components of the graph, so each independent part of the pipeline is listed on its own. Within a section, targets appear in the order they can be built: a target comes after those it needs, and targets at the same depth are listed alphabetically.

With names, only those targets and their ancestors are listed; descendants = true adds everything downstream of them (as in tar_dot). The store is not consulted. tar_list() loads _targets.jl.

source
Targets.TargetList Type
julia
TargetList

The targets of a pipeline, returned by tar_list: components holds one NamedTuple per connected component of the graph, with the fields constants, inputs, computations and outputs, each a vector of names. Prints as a sectioned list.

source
Targets.tar_status Function
julia
tar_status(p::Pipeline; names = nothing, descendants = false,

A DotGraph: Graphviz DOT for the pipeline, laid out left to right and coloured by status (up to date, outdated, errored, not built). With names, only those targets and their ancestors are drawn; descendants = true adds everything downstream of them. Targets.tar_visnetwork Function
julia
tar_visnetwork(p::Pipeline; names = nothing, descendants = false, status = true,
               store = default_store_path(), root = nothing, figure_size = (900, 500),
               interactive = nothing)

Plot the pipeline with the same layout, colours and subgraph selection as tar_dot, returning a Makie Figure. Needs a Makie backend (using CairoMakie, GLMakie or WGLMakie). File targets are squares, branching targets show their branch count, and colours show status.

An interactive figure opens in a window (GLMakie) or fills a browser tab (WGLMakie), resizing with it (figure_size is only its starting size), and can be rearranged there:

  • drag a target to move it (its edges and label follow); dragging a selected target moves the whole selection;

  • click a target to select it, shift-click to add it to the selection (or remove it), shift-drag to select every target in an area, and click the background to clear the selection;

  • drag the background or use the right mouse button to pan, scroll to zoom, and ctrl-click to reset the view.

A side panel hides targets: uncheck a kind (constants, input files, computations, output files) or a status (up to date, outdated, ...) to hide those targets, use "Hide selected" to hide the selection or "Show only selected" to hide everything else, and "Show all" to undo all hiding. Under "Also show", switch on "Dependencies" or "Descendants" to bring back everything upstream or downstream of the targets still shown, however it was hidden (e.g. after hiding a selection, to restore the targets the rest need). What a switch shows is fixed when it goes on and does not count what the other one shows; switching it off hides those targets again. Edges to hidden targets are hidden too.

By default (interactive = nothing) the figure is interactive exactly when GLMakie or WGLMakie is the active backend. interactive = false always gives a static figure, and interactive = true errors under any other backend.

Targets.tar_picker Function
julia
tar_picker(p::Pipeline; store = default_store_path(), root = nothing,
           input = stdin, io = stdout)
tar_picker(; script = default_script(), kwargs...)

Pick targets with a fuzzy finder in the terminal, then an action to run on them, for exploring a pipeline at the REPL.

Type to narrow the list of targets (in tar_list order) to those whose names contain the typed characters in order, best matches first: fm matches fit_model, and space-separated terms must all match. Tab selects the target under the cursor (shift-tab moving up instead), ctrl-a selects every match (or unselects them all), and enter finishes; enter without a selection picks the target under the cursor. Up and down move, ctrl-u clears the query, and Esc or ctrl-c cancels.

Then choose the action the same way, by typing part of its name:

  • tar_make: build the picked targets and what they need;

  • tar_invalidate: forget their metadata, so they rebuild next time;

  • tar_status: list them and their dependencies with their status;

  • tar_visnetwork: plot them and their dependencies (needs a Makie backend).

The equivalent call is printed before it runs, and its result is returned (nothing if cancelled). tar_picker() loads _targets.jl.
